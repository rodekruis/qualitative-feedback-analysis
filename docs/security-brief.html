Security & Privacy Brief

Qualitative Feedback Analysis service — how humanitarian feedback data is protected, end to end.

13 August 2026 · rodekruis/qualitative-feedback-analysis
❖

No feedback text, prompts, or beneficiary personal data are ever stored permanently. Identifying details are held only in memory for the duration of processing, then discarded — the database retains only operational metadata (which National Society made the call, operation type, counts, cost, timing), never the feedback content itself.

Authentication & Access

  • Bearer-token authentication required on every endpoint except the health check.
  • Two key types: tenant keys scoped to a single organisation, and a small number of superuser keys with cross-tenant authority — create/delete tenants, issue or revoke API keys, view usage across all tenants.
  • Tenant keys are hashed at rest (scrypt) in the database and compared in constant time — never stored or logged in plain text.
  • Superuser keys are stored as plaintext secrets in Azure Key Vault — protected by Key Vault RBAC and access logging — rather than hashed in the database, since they must exist before the app can reach its own data store.

Privacy & PII Handling

  • Every AI call is wrapped anonymise → send → de-anonymise; the model never sees raw personal data. Presidio + spaCy
  • Analysis output never re-identifies named individuals.
  • Data minimisation by design: feedback content and model responses are never written to the database.
  • Currently powered by OpenAI's GPT-5.4 model — accessed through Azure AI Foundry (Microsoft-hosted, Sweden Central), not OpenAI's servers. Prompts and completions are never available to OpenAI, never used to improve their models, or to train foundation models without explicit permission. Source

Secrets & Key Management

  • Infrastructure secrets — LLM API credentials, database access, superuser bootstrap keys — live in Azure Key Vault; injected into the app as configuration, never touched by application code directly.
  • Tenant API keys are not in Key Vault at all — they're stored hashed in the application database.
  • Deployments authenticate to Azure via short-lived, keyless credentials (OIDC) — no long-lived deployment secrets.
  • Secret values are excluded from source control and infrastructure state files.

Audit & Monitoring

  • Every request carries a traceable correlation ID from entry to completion.
  • Feedback content, prompts, model output and key values are never written to logs — enforced in code.
  • Centralised monitoring with automated alerts on errors, downtime and resource strain.
  • The database stores only call metadata — tenant ID, operation type, token counts, cost, latency, error class — never feedback text, prompts or model output. Queryable via a tenant-scoped usage/audit API.

Network & Infrastructure

  • The database has no public network access and no password login — private network only, identity-based access.
  • TLS 1.2+ enforced everywhere; legacy insecure file-transfer protocols are disabled.
  • Services authenticate to each other via managed identity — no shared-key secrets between components.
  • Isolated environments: development, staging and production each have their own resources.
  • Hosted in Europe (Sweden) — data stays within the EU.

Secure Development

  • Static security scanning (CodeQL) and security-focused lint checks run on every change.
  • Automated dependency scanning keeps third-party libraries patched.
  • Architectural boundaries are enforced by the build, not convention — the privacy-sensitive core stays isolated from vendor code.
  • Releases require a named human's sign-off before reaching staging or production.
